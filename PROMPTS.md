It details the initial prompts provided to the AI, the generated code, critical security vulnerabilities detected upon code review, the manual engineering fixes implemented by the student, and the corresponding Git commit links.

## Entry 1: Project Setup and Initial Entity Models
- **Date**: November 5, 2026
- **Phase**: Architecture & Domain Modeling
- **Git Commit**: `feat: initial project structure and configuration` (`0915074`)

### 1. Prompt Given to AI
> "Create Spring Boot JPA entity models for `User` and `Account`. The account should have an account number and a balance field to store how much money the user has."

### 2. Code Generated by AI
```java
@Entity
@Table(name = "accounts")
public class Account {
    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;
    
    private String accountNumber;
    private double balance; // Generated as primitive double
    
    // Getters and setters...
}
```

### 3. Critical Security Vulnerability Detected
- **Vulnerability**: **Financial Precision Loss & Floating-Point Rounding Drift**.
- **Risk Analysis**: In Java, `double` and `float` use IEEE 754 binary floating-point representation. Calculations such as `0.1 + 0.2` yield `0.30000000000000004`. Over thousands of high-frequency banking transactions, rounding drift creates fractional cent leakage, ledger discrepancies, and potential negative balance exploitation. Furthermore, the column lacked database-level non-null and uniqueness constraints.

### 4. Manual Fix Applied by Student
- **Code Refactor**: Replaced `double` with `java.math.BigDecimal` specifying 19 digits with 4 decimal places (`DECIMAL(19, 4)`).
- **Constraints Added**: Added `@Column(precision = 19, scale = 4, nullable = false)`, `unique = true` on `accountNumber`, and defined database check constraints `balance >= 0.0000`.
```java
@Column(name = "balance", precision = 19, scale = 4, nullable = false)
private BigDecimal balance = BigDecimal.ZERO.setScale(4, RoundingMode.HALF_UP);
```
- **Security Rationale**: Exact arithmetic precision is non-negotiable in financial ledgers. All operations must explicitly define rounding modes (`RoundingMode.HALF_UP`).

## Entry 2: Money Transfer Endpoint & Broken Object-Level Authorization (IDOR)
- **Date**: November 7, 2026
- **Phase**: Transaction Processing
- **Git Commit**: `feat: secure money transfer service with concurrency locking and idempotency` (`0ad6686`)

### 1. Prompt Given to AI
> "Create a Spring Boot REST controller and service for money transfers. The request should take the sender's account ID, recipient's account ID, and the amount to transfer."

### 2. Code Generated by AI
```java
@PostMapping("/transfer")
public ResponseEntity<?> transferMoney(@RequestBody TransferRequest request) {
    // Controller accepts senderAccountId directly from client body
    transferService.executeTransfer(
        request.getSenderAccountId(), 
        request.getRecipientAccountId(), 
        request.getAmount()
    );
    return ResponseEntity.ok("Transfer successful");
}
```

### 3. Critical Security Vulnerability Detected
- **Vulnerability**: **OWASP A01:2021 &mdash; Insecure Direct Object Reference (IDOR)**.
- **Risk Analysis**: The endpoint blindly trusted `request.getSenderAccountId()` supplied by the client. Any authenticated attacker could simply alter the `senderAccountId` in the HTTP JSON request payload to withdraw money from arbitrary victims' bank accounts without their consent or knowledge.

### 4. Manual Fix Applied by Student
- **Code Refactor**: Completely removed `senderAccountId` from `TransferRequest.java`.
- **Authoritative Context Binding**: The sender is authoritatively retrieved on the server side from the authenticated Spring Security context using `SecurityUtils.getCurrentUserId()`.
```java
// TransferController.java
Long currentUserId = SecurityUtils.getCurrentUserId();
TransferResponse response = transferService.transfer(
    currentUserId, 
    request.getRecipientAccountNumber(), 
    request.getAmount(), 
    request.getIdempotencyKey(), 
    request.getDescription()
);
```
- **Security Rationale**: Never trust client-supplied identity parameters for state-changing or sensitive financial operations. The server-side authentication token must be the sole authority determining the debtor.

## Entry 3: Race Conditions, Double-Spending & Deadlock Prevention
- **Date**: November 9, 2026
- **Phase**: Concurrency & Transaction Integrity
- **Git Commit**: `feat: database entities and repositories with pessimistic locking` (`7703f90`)

### 1. Prompt Given to AI
> "Write the logic inside `TransferService` to deduct money from the sender and add it to the receiver. Make sure the sender has sufficient balance before doing the transfer."

### 2. Code Generated by AI
```java
@Transactional
public void transfer(Long senderId, String recipientAccNum, BigDecimal amount) {
    Account sender = accountRepository.findByUserId(senderId);
    Account receiver = accountRepository.findByAccountNumber(recipientAccNum);
    
    // Check balance
    if (sender.getBalance().compareTo(amount) < 0) {
        throw new RuntimeException("Insufficient balance");
    }
    
    sender.setBalance(sender.getBalance().subtract(amount));
    receiver.setBalance(receiver.getBalance().add(amount));
    
    accountRepository.save(sender);
    accountRepository.save(receiver);
}
```

### 3. Critical Security Vulnerability Detected
- **Vulnerability**: **Time-of-Check to Time-of-Use (TOCTOU) Race Condition & Unordered Lock Deadlock**.
- **Risk Analysis**: 
  1. **Double-Spending**: If a user with $100 balance submits 5 simultaneous transfer requests of $100 across parallel connections, all 5 threads read the balance as $100 before any thread writes back the deduction. All 5 requests succeed, resulting in a -$400 balance (theft of funds).
  2. **Deadlock**: If User A transfers to User B while User B concurrently transfers to User A, Thread 1 locks Account A and waits for Account B, while Thread 2 locks Account B and waits for Account A. Both transactions hang and trigger `DeadlockLoserDataAccessException`.
  3. **Stale Hibernate Cache**: Calling standard `findByUserId` before locking places the entity in Hibernate's first-level cache. Subsequent locking queries might return stale memory state without reading the latest committed database state.

### 4. Manual Fix Applied by Student
- **Code Refactor**:
  1. Created `findByIdWithLock` in `AccountRepository` with `@Lock(LockModeType.PESSIMISTIC_WRITE)`.
  2. Enacted **Deterministic Lock Ordering**: Always lock `Math.min(sender.getId(), receiver.getId())` first, followed by `Math.max(...)`.
  3. Added explicit `entityManager.refresh()` to force Hibernate to synchronize with latest committed row data under the lock.
```java
// Deterministic lock ordering to prevent cross-transfer deadlocks
Long firstId = Math.min(senderAccount.getId(), receiverAccount.getId());
Long secondId = Math.max(senderAccount.getId(), receiverAccount.getId());

Account firstLocked = accountRepository.findByIdWithLock(firstId)
    .orElseThrow(() -> new ResourceNotFoundException("Account", "id", firstId));
Account secondLocked = accountRepository.findByIdWithLock(secondId)
    .orElseThrow(() -> new ResourceNotFoundException("Account", "id", secondId));

// Discard stale L1 cache and load actual row state
entityManager.refresh(firstLocked);
entityManager.refresh(secondLocked);
```
- **Security Rationale**: Pessimistic write locks at the SQL engine level (`SELECT ... FOR UPDATE`) serialize concurrent transactions. Deterministic sorting eliminates circular wait conditions, mathematically preventing deadlocks.

## Entry 4: JWT Authentication and Role Escalation
- **Date**: November 10, 2026
- **Phase**: Authentication & Authorization
- **Git Commit**: `feat: authentication and authorization with Spring Security and JWT` (`7ac13a7`)

### 1. Prompt Given to AI
> "Implement JWT authentication in Spring Security so users can log in and access protected endpoints."

### 2. Code Generated by AI
```java
@Bean
public SecurityFilterChain filterChain(HttpSecurity http) throws Exception {
    return http
        .csrf(csrf -> csrf.disable())
        .authorizeHttpRequests(auth -> auth
            .requestMatchers("/api/auth/**").permitAll()
            .anyRequest().authenticated()
        )
        .build();
}
```

### 3. Critical Security Vulnerability Detected
- **Vulnerability**: **Missing Role-Based Access Control (RBAC) & Secret Key Rigidity**.
- **Risk Analysis**: 
  1. The security filter chain authenticated any valid token but enforced no role checks on administrative endpoints (e.g., `/api/admin/users/{id}/status`). A normal user (`ROLE_USER`) could send HTTP requests to ban other users or elevate their own privileges.
  2. The generated JWT parser did not enforce modern JJWT 0.12 cryptographic signature requirements, potentially allowing algorithm switching attacks.

### 4. Manual Fix Applied by Student
- **Code Refactor**:
  1. Configured explicit URL path authorization in `SecurityConfig`:
     ```java
     .requestMatchers("/api/admin/**").hasRole("ADMIN")
     .requestMatchers("/api/users/**", "/api/transfers/**").hasAnyRole("USER", "ADMIN")
     ```
  2. Added `@EnableMethodSecurity(prePostEnabled = true)` and annotated `AdminController` with `@PreAuthorize("hasRole('ADMIN')")`.
  3. Configured `JwtTokenProvider` using JJWT `Jwts.parser().verifyWith(secretKey).build()` with HMAC-SHA256 signature verification.
  4. Added `CustomUserDetailsService` with database role mapping `ROLE_` prefixing.
- **Security Rationale**: Defense-in-depth requires dual-layer authorization: URL path pattern matching at the network perimeter filter level and method-level security at the service/controller level.

## Entry 5: Immutable Audit Logging & Transaction Rollback Vulnerability
- **Date**: November 11, 2026
- **Phase**: Audit Integrity & Oversight
- **Git Commit**: `feat: immutable audit logging and admin oversight` (`eb478b0`)

### 1. Prompt Given to AI
> "Create an audit service that logs every transfer. Call it inside `TransferService` so we know when transfers happen."

### 2. Code Generated by AI
```java
@Service
public class AuditService {
    @Autowired
    private AuditLogRepository auditLogRepository;

    public void log(Long userId, String action, String description) {
        AuditLog log = new AuditLog(userId, action, description, LocalDateTime.now());
        auditLogRepository.save(log);
    }
}
```

### 3. Critical Security Vulnerability Detected
- **Vulnerability**: **OWASP A09:2021 &mdash; Security Logging and Monitoring Failures (Audit Loss on Rollback)**.
- **Risk Analysis**: In Spring, when an exception occurs inside a `@Transactional` boundary (such as `InsufficientBalanceException` or `AccountInactiveException`), the transaction manager initiates a full database rollback. Because `AuditService.log()` participated in the caller's existing transaction, the audit record was rolled back too! Consequently, all unauthorized or suspicious failed transfer attempts vanished without a trace, blinding administrators to ongoing brute-force or fraud attacks.

### 4. Manual Fix Applied by Student
- **Code Refactor**:
  1. Configured independent transaction propagation in `AuditService.java`:
     ```java
     @Transactional(propagation = Propagation.REQUIRES_NEW)
     public void log(Long actorId, String action, String description) {
         AuditLog auditLog = new AuditLog(actorId, action, description);
         auditLogRepository.save(auditLog);
     }
     ```
  2. Modified `AuditLogRepository` to be strictly append-only: removed update and delete methods.
  3. In `TransferService.java`, wrapped business operations in explicit try/catch blocks that invoke `auditService.log(...)` for both successful transfers (`TRANSFER_SUCCESS`) and failed attempts (`TRANSFER_FAILED_INSUFFICIENT_FUNDS`, `TRANSFER_FAILED_INACTIVE_ACCOUNT`, etc.) before re-throwing the exception.
- **Security Rationale**: Security audit trails must be decoupled from business transaction lifecycles (`Propagation.REQUIRES_NEW`). A banking ledger must retain an immutable record of every rejected transaction for compliance, fraud detection, and regulatory non-repudiation.
